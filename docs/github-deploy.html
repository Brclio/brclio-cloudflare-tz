第一次部署，还是从上传 ZIP 迁移？

当前情况接下来怎么做
还没有部署从下一节 Fork 开始，直接创建一个新的 Pages Git 集成项目。
已有 Pages Git 项目先核对第 4、5 节的配置，再去第 6、7 节检查自动部署和同步。
已有拖放 ZIP 项目保留旧项目，使用新名称创建 Git 项目；验证通过后再迁移自定义域。

Direct Upload 不能原地切换成 Pages Git 集成。
Cloudflare 官方要求新建 Git 集成项目。即使旧项目的设置中出现「Git 存储库 / 连接」，也不要据此假定已经转换成功。官方说明 ↗

迁移旧项目：怎样保留设置和访问入口？
  1. 先在旧后台导出备份。

    从「设置」导出主配置；在「订阅管理 → 自定义优选地址」复制 ADD.txt 全文另存；可选的 Cloudflare 用量与 Telegram 凭据，从自己的安全记录在新环境重新填写。主配置导出不包含这些内容。记录当前 UUID、HOST、其他机密与 KV 命名空间；不要把这些值写进 GitHub。

  2. 新建不同名称的 Pages Git 项目。

    例如 my-edge-git。先使用新项目的 *.pages.dev 地址。建议用独立 KV 导入备份进行验证；若绑定旧 KV，两套程序会读写同一份数据，测试保存也会影响旧实例。

  3. 先验证新项目，再移动正式域名。

    新后台登录、配置保存与客户端连接通过后，安排迁移：在旧 Pages 项目移除该自定义域，再在新项目关联，按新项目提示更新 CNAME。等待域状态和 HTTPS 正常，再更新客户端订阅。

  4. 保留旧项目作为退路。

    更换项目会得到新的 pages.dev 地址。固定 UUID 可保留节点身份，但订阅 token、域名相关链接仍要以新后台生成结果为准。稳定运行前，保留旧项目和备份。

域名关联与 DNS 规则见 Cloudflare 自定义域说明 ↗。

✓

这一步完成时已确定新建或检查哪个 Pages 项目；已有实例的配置和访问入口已记录。

03
CONNECT THE REPOSITORY

把 Pages，接到这份代码上。

Cloudflare 同时有 Workers 和 Pages 的 Git 入口。本篇需要 Pages 的「导入现有 Git 存储库」。先进入 Pages，再选 GitHub。

操作路径Workers 和 Pages→创建应用程序→Pages 开始使用→导入现有 Git 存储库
  1. 从创建应用页面进入 Pages。

    如页面顶部出现 Make something new，按下图寻找底部「想要部署 Pages？开始使用」。部分版本直接显示 Pages 标签或 Connect to Git，选择 Pages 对应入口即可。

  1. 选择上方的「导入现有 Git 存储库」。

    下图同时展示 Git 和拖放两条路线。此处点击上方选项的「开始使用」。

  1. 连接 GitHub 并授权自己的仓库。

    登录刚才 Fork 使用的 GitHub 账号。授权页可选择 Only select repositories，勾选自己的 brclio-cloudflare-tz，按页面完成安装与授权。组织仓库可能需要组织管理员批准。

  2. 选中自己的 Fork，开始设置。

    返回 Cloudflare，选择自己的账号和仓库，继续到构建配置。核对仓库所有者是自己的用户名；后续推送必须发生在这个仓库才会触发该项目更新。

i

第一次构建成功后，还要配置运行环境。
此时打开 /admin 可能提示缺少 ADMIN 或 KV。这表示程序已经启动，但下一节的机密和存储还没接好。

仓库有 wrangler.toml，需要修改它吗？

按本篇的 Pages 控制台路线部署时，不需要修改现有 wrangler.toml。它用于 Workers 部署和本地运行，含 main = "dist/_worker.js" 与全零的本地 KV 占位 ID；本篇由 Pages 控制台管理真实机密和绑定。

不要直接补一个 pages_build_output_dir 就部署：这个字段会启用 Pages 的 Wrangler 配置管理，需要先完整转换配置并检查真实绑定。Cloudflare 明确区分 Workers 与 Pages 的配置字段。Wrangler 配置迁移说明 ↗

GitHub Actions 出现绿色勾，是否已经更新 Cloudflare？

本仓库的 .github/workflows/verify.yml 运行构建、语法检查和测试，并上传打包产物。它没有 Cloudflare 发布步骤。实际发布由刚连接的 Pages Git 集成 完成，要在 Cloudflare 检查部署状态和提交编号。

若 Fork 的 Actions 尚未启用，可在自己的仓库 Actions 页面按提示启用工作流。启用后能获得额外测试结果，但 Pages 构建与 Actions 分别运行；Actions 失败不会自动阻止 Pages 发布。需要合并前检查时，在分支完成测试再合入 main。

05
CODE AND PRIVATE SETTINGS

代码自动更新，配置另有归处。

GitHub 存程序。Cloudflare 的机密存密码和节点身份。KV 存后台的运行配置。把它们分别接好，后续更新才不会误把私人配置写进源码。

Production / 生产

三项必要配置

在 Pages 项目「设置」中选择生产环境，逐项添加。

名称类型填写内容
ADMIN机密 / Secret自己的高强度后台密码不要使用截图里的演示密码
UUID机密 / Secret自己生成并固定保存的 UUID v4已有实例迁移时可沿用自己的固定 UUID
KVKV 命名空间绑定自己的配置命名空间绑定名称必须为大写 KV
  1. 创建 KV 命名空间。

    到「存储和数据库 → Workers KV」新建，例如 my-edge-config。已有可复用空间时先确认用途；独立测试使用单独的 KV。完整创建截图见 基础教程第 3 节。

  2. 添加生产机密。

    回到 Pages 项目 → 设置 → 变量和密钥 → 添加。名称分别为 ADMIN 与 UUID，类型选择「机密」或按界面选「Encrypt / 加密」后保存。NODE_VERSION 是普通构建变量，保留第 4 节的设置。

点击生成你自己的 UUID v4

UUID 在当前浏览器本地生成，不发送到服务器。生成一次并妥善保存，之后更新代码无需重新生成。

  1. 添加 KV 绑定。

    设置 → 绑定 → 添加 → KV 命名空间。变量名称填 KV，下拉选择刚才创建的命名空间，保存。不要把 KV ID 填进普通文本环境变量。

  1. 发起新的生产部署。

    回到 Deployments / 部署，对 main 的当前提交使用 Retry deployment / 重试部署 或页面的重新部署操作。没有该入口时，可按下一节在自己的 main 提交一次维护说明来触发新构建。保存机密或绑定后，必须等新部署成功。

  2. 登录并检查保存。

    打开 https://你的项目.pages.dev/admin，使用 ADMIN 登录。在后台修改一项可恢复的普通设置，保存后刷新，确认能读回。需要正式域名时，按 基础教程的域名步骤 关联自己的域名，再生成客户端订阅。

Cloudflare 的 KV 绑定 和 Secrets 说明均要求在使用新配置的部署之前完成设置。

分支预览要不要配置同样的机密和 KV？

Production 与 Preview 分开管理。需要在预览地址测试登录和保存时，给 Preview 设置单独的 ADMIN、UUID 和独立测试 KV，再创建新的预览部署。不要让测试页面共用生产 KV 后随意修改配置。

暂不需要预览时，可在构建和部署的分支控制中把预览部署设为 None，保留 main 的自动生产部署。分支部署控制 ↗

06
ONE COMMIT, ONE DEPLOYMENT

亲手验证一次自动更新。

保存一份普通维护记录，用一次小提交检查「GitHub → Pages」是否真的连通。先验证部署触发，再根据后续实际代码变更验证页面和功能。

  1. 在自己的 GitHub 仓库创建说明文件。

    选择 main，点击 Add file → Create new file，文件名填写 maintenance-notes.md，写一句「已连接 Cloudflare Pages Git 自动部署」。只记录维护说明，不放密码、UUID、订阅链接或账户信息。

  2. 提交这次修改。

    点击 Commit changes，提交说明可以写 docs: record Pages setup。个人测试仓库可提交到 main；若分支规则要求 Pull Request，按规则创建并合并 PR。记下新的提交短 SHA。

  3. 到 Cloudflare 看新部署。

    Pages 部署列表应新增对应 main 提交。等待构建成功，比较部署详情中的 SHA 与 GitHub 的提交。确认生产地址指向此次部署。

  4. 重新检查后台。

    用正式生产地址打开 /admin，确认登录、配置读取和保存正常。这次只改维护文件，所以界面没有变化是正常的；成功证据是新的提交进入了生产部署。

「实时更新」是提交后的自动部署。
Cloudflare 需要排队、安装依赖和构建，不是保存文件后立刻刷新。只有提交到所连接仓库的生产分支，并且构建成功，才更新生产站点。若设置了构建监听路径，请让验证文件的路径匹配规则。

自动构建与提交的关系参见 Git 集成概览；自定义触发路径参见 构建监听路径。

✓

这一步完成时GitHub 新提交与 Pages 生产部署的 SHA 一致；无需手动上传 ZIP 即完成了一次发布。

07
KEEP UP, KEEP YOUR CHANGES

上游更新后，主动同步一次。

Fork 不会因为作者发布了新版就自行更新。你先查看更新内容，再把变更合入自己的 main；Pages 随后按已经设置好的流程发布。

日常更新：用 GitHub 网页同步

  1. 先看更新内容，保存备份。

    打开 项目 Releases ↗ 和最近提交，留意配置迁移或不兼容变更。导出当前配置，记下仍可用的生产部署 SHA。

  2. 打开自己的 Fork，选择 main。

    点击文件列表上方的 Sync fork，查看待同步的提交。出现 Update branch 时，确认后同步。若显示已经同步，无需反复操作。

  3. 检查自动部署结果。

    同步使自己的 main 产生新提交后，去 Pages 等待构建。再次比对提交 SHA；然后登录、保存、更新订阅，并在客户端测试真实连接。

!

出现冲突时，先保留自己的修改。
GitHub 会提示通过 Pull Request 处理冲突。不要为了一键同步直接丢弃个人提交。逐个核对冲突文件，合并后检查与测试；不确定时暂缓合入，旧生产部署仍可继续运行。

网页同步、冲突提示及本地同步方式依据 GitHub 官方同步 Fork 指南 ↗。

只想跟随稳定 Release，不想同步所有 main 提交

Sync fork 同步的是上游分支当前状态，可能包含最新 Release 之后的提交。需要固定发布版本时，先阅读对应 Release 的标签与提交；在自己的更新分支中合入那个明确版本，通过检查后再合入生产分支。

不要把「仓库已同步」等同于「已锁定某个 Release」。部署详情中的 SHA 才是这次生产运行代码的精确来源。

有自己的代码改动？在本地分支检查后再合入

以下命令需要本地 Git 和 Node.js 22 或更高版本。把 YOUR_USERNAME 替换成自己的 GitHub 用户名。不要原样复制占位用户名。

TERMINAL / 首次克隆自己的 Fork
git clone https://github.com/YOUR_USERNAME/brclio-cloudflare-tz.git
cd brclio-cloudflare-tz
git remote add upstream https://github.com/Brclio/brclio-cloudflare-tz.git
git remote -v

确认 origin 指向自己、upstream 指向 Brclio。已经配置过 upstream 时，不要重复添加；先用 git remote -v 核对。

TERMINAL / 每次同步，在干净工作区执行
git status
git switch main
git pull --ff-only origin main
git fetch upstream
git switch -c maintenance/sync-upstream
git merge upstream/main
npm ci
npm run check
npm test
npm run build

运行前让 git status 显示没有待处理修改；有自己的改动就先提交到个人分支。更新分支名可加日期，避免与上次重名。命令按顺序执行，任一步报错先停下来处理；git pull --ff-only 失败说明本地和远端分叉，需要先确认各自提交。

git merge 报冲突：接下来具体做什么？
  1. 运行 git status 查看冲突文件，在编辑器中逐段比较双方修改，删除冲突标记并保留正确代码。
  2. 只添加已解决的文件，例如 git add public/assets/app.css；按实际文件名逐个处理。然后运行 git commit 完成合并。
  3. 重新执行依赖安装、检查、测试与构建。无法判断正确结果时，可在合并进行中使用 git merge --abort 取消本次合并，保留更新前的分支状态后再处理。

不要使用强制推送或清空个人改动来代替解决冲突。图形化说明可参考 GitHub 命令行冲突解决指南 ↗。

TERMINAL / 检查通过后，推送更新分支
git push -u origin maintenance/sync-upstream

如果创建分支时改了名字，上面的推送命令也使用同一个分支名。随后在 自己的仓库 创建 Pull Request：base repository 选自己的 Fork，base 选 main，compare 选更新分支。Fork 的 PR 页面有时默认指向上游，合并前务必核对。检查通过后合并，Pages 才更新生产。若开启预览部署，可以先验证分支预览；预览的配置按第 5 节单独设置。

✓

这一步完成时知道如何同步上游；有个人改动时，能够先在更新分支处理和验证，再合入自己的生产分支。

08
A WAY BACK

更新之前，把退路准备好。

代码版本、Cloudflare 配置和 KV 数据是三份不同的东西。恢复旧部署只处理部署版本，数据备份需要另外准备。

保存什么在哪里保存恢复时的用途
代码版本GitHub 提交 SHA、Release 标签、Pages 成功部署记录回到可用程序版本，比较引入问题的改动。
环境配置自己保存机密值；记录 Production / Preview 的绑定与变量名重建项目时恢复 ADMIN、UUID、HOST 等配置。
后台主配置后台「设置」导出的配置文件恢复节点、路由等主设置；不要上传到公开仓库。
独立数据复制 ADD.txt 地址文本另存；独立保管 Cloudflare 用量与 Telegram 凭据主配置备份未包含的内容需要单独恢复。

新版本异常：先把生产指向旧部署

  1. 找到之前验证成功的生产部署。

    打开 Pages → Deployments → All deployments。根据自己保存的 SHA 和时间选择目标；预览部署不能作为生产回滚目标。

  2. 执行部署回滚。

    在目标部署的「⋯」菜单选择 Rollback to this deployment，核对目标版本后确认。回到正式域名检查后台、订阅和客户端连接。

  3. 处理仓库中的问题提交。

    回滚不会把 GitHub 的 main 自动改回去。需要修复或撤销问题代码，再经检查合入；否则下一次生产提交可能再次发布有问题的代码。排查期间可临时关闭生产分支自动部署，处理完成后恢复。

可回滚目标和操作路径：Pages 回滚文档 ↗。自动部署开关：分支部署控制 ↗。

!

KV 数据不会随代码回滚。
KV 是部署之外的存储。新版本已写入的设置，不会因为切回旧程序就自动恢复；这来自本项目「程序 + KV」的结构。若需要恢复数据，用已保存的备份逐项恢复，并确认旧版本兼容。机密与绑定也要分别核对，不能把回滚当作整个账号的快照。

KV 的独立读写与缓存行为参见 Workers KV 工作方式。跨地区读取可能短暂看到旧值，恢复后需要重新读取核对。

✓

这一步完成时有可用部署的 SHA、所需配置备份和独立数据；知道去哪里回滚，也知道回滚后还要处理仓库与数据。

09
FIND THE NEXT STEP

卡住时，先看是哪一层。

仓库权限、构建、运行配置和真实连接各有自己的成功条件。找到第一条具体错误，再按这一层处理。

Cloudflare 的列表中找不到自己的 GitHub 仓库

确认 GitHub 当前登录账号、Fork 所有者和 Cloudflare 授权对象一致。到 GitHub 的 Installed GitHub Apps 检查 Cloudflare Pages 的仓库访问范围，把自己的 Fork 加入已授权列表，再回 Cloudflare 刷新。组织仓库需检查组织批准与权限。官方授权说明 ↗

看到 Deploy command / npx wrangler deploy，该怎么填？

先确认是不是误进 Workers Builds。本文使用 Pages Git 集成，应有构建输出目录。返回创建入口，进入 Pages，再导入 Git 存储库。不要把本篇 dist/pages 配置与 Workers 部署命令混用。

npm ci 失败，提示锁文件、Node 或找不到 package.json

找不到 package.json：把 Root directory 还原为仓库根目录。Node 版本不符合：设置 NODE_VERSION=22 后重新构建。锁文件不一致：检查自己是否只修改了 package.json；在本地使用兼容 Node/npm 更新并核对锁文件、运行测试，再提交两个文件。不要删锁文件或改成跳过错误来掩盖问题。

构建成功，但页面显示占位文字、404 或没有后台

核对构建命令为 npm ci && npm run build、输出目录为 dist/pages，并确认日志生成了完整 Worker。不要填写 public、docs 或仅 dist。用生产地址的 /admin 检查；如果仍显示占位页，查看部署中的 _worker.js 是否位于输出根目录。

配置了 ADMIN / KV，仍提示缺失

确认设置的是 Production，而不是只设置 Preview。ADMIN 名称应为大写且类型为机密；KV 必须是资源绑定，名称为大写 KV。保存后创建新的生产部署，并核对部署时间晚于配置修改。

GitHub 提交了，Pages 为什么没有新部署？

确认提交进入 Pages 连接的仓库和 main。未合并的分支或 PR 通常只是预览，不更新生产。再核对 GitHub 授权、自动生产部署开关、构建监听路径和提交中是否含跳过构建标记。Pages 部署日志与 GitHub Actions 是两处独立结果。

作者发布新版本，我的 Fork 为什么没变化？

Pages 只监听你连接的仓库。去自己的 Fork 使用 Sync fork → Update branch；同步产生新提交后才会触发部署。每次同步前先看更新说明，确认是否涉及迁移，并保存配置备份。

Sync fork 提示冲突，或更新分支比上游多提交

多出的提交可能是自己的定制，不代表出错。检查有哪些文件被双方修改，在分支中合并并解决冲突，测试通过后合回自己的 main。不要直接选择丢弃个人改动，也不要盲目强推。

新提交 SHA 一致，页面看起来却没变化

先确认改动是否影响运行界面；维护说明和教程文字不一定进入后台程序。若确实改了前端，使用正式生产地址，关闭旧标签后重新打开或强制刷新，并核对是否访问了历史预览地址。

回滚成功，为什么配置还是新版本的？

代码部署与 KV 数据分开。回滚把生产流量切回旧程序，不会恢复 KV 备份。按第 8 节分别恢复需要的数据，并核对旧程序与当前数据的兼容性。

能登录、能保存，客户端仍不能连接

程序发布成功不等于实际连接成功。使用正式域名重新生成订阅，核对客户端的 UUID、协议、传输、端口与路径，再查看实际连接日志。完整订阅步骤见 部署与使用手册。

没有找到对应条目。试试「仓库」「构建」「KV」或「更新」。

10
READY FOR THE NEXT CHANGE

下一次更新，按这条路线走。

知道来源，也知道结果。

每次生产运行都对应一个 Git 提交；每次合入之前知道改了什么；每次发布之后都检查实际功能。日常维护就有了清楚的顺序。

  1. 查看更新并备份读 Release 与变更，保存配置和独立数据，记下可用 SHA。
  2. 同步或修改自己的仓库有定制时先用分支处理冲突、检查和测试，再合入 main。
  3. 核对 Pages 发布新的生产部署成功，SHA 与自己的 main 提交一致。
  4. 验收真实功能登录、配置读写、订阅更新、客户端连接均通过；异常时使用备份与回滚流程。
