# 代理连接与测速说明（v1.0.7）

基于 `cmliu/edgetunnel` 的 `448a83ced00a43c1d892d5ecbed86a26ea9eeaff`，保留转发队列、合包与主要回退策略，修复握手、路由、额外等待与请求串扰。v1.0.7 的完整对照和仍未解决的传输限制见 [代理深度排查](proxy-deep-audit.md)。以下公网样本属于本轮修复前的部署，不是 v1.0.7 的线上验收。

## v1.0.6：Clash Verge 手动测速的 HTTP 400

实际排查发现，Clash Verge 2.5.2 的手动选择组在没有组内或全局自定义测试地址时，使用 `http://cp.cloudflare.com/generate_204`；自动选择组可以同时使用订阅中的 gstatic 地址。只查看订阅里的自动检测 URL，不能确定手动测速的目标。[对应版本的客户端源码](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.2/src/components/proxy/proxy-head.tsx#L63-L70)

v1.0.5 移除本地 204 后，暴露出原有 ProxyIP 解析默认端口为 443 的问题：HTTP 80 请求直连失败后，原始明文被发送到 HTTPS 端口。实测收到 **HTTP 400 / The plain HTTP request was sent to HTTPS port**。这个结果是兼容缺陷，不能仅解释为完整链路较慢；Mihomo 延迟 API 返回数字也不证明目标返回了 204。

v1.0.6 让无端口 ProxyIP 在目标为 80 时默认连接 80；其他目标端口仍保持原默认 443。显式端口、`.tpNNN` 保留，TXT 自带端口优先于父级端口，裸 TXT 条目继承父级端口。不会恢复合成 204，也不会改变数据内容或新增请求重放。

真实 Cloudflare 检测端点还可能返回 `Connection: close`，而旧版本地 204 会保持连接。因此，即使修复 400，Clash 的统一延迟也不一定能完成第二次请求，数字不能与旧版本地 204 直接比较。建议把“节点选择”组的手动测速 URL 设为 `http://www.gstatic.com/generate_204`，与现有自动检测保持一致；若设过组内地址，其优先级高于全局默认值。

2026-09-18 使用同一 Mihomo v1.19.29、相同 4 组入口 IP / 端口、WS / TLS、统一延迟，在两个现有部署间交替测量，结果如下。测试在隔离进程进行，没有切换用户正在使用的订阅。

| 测试目标 | 原版部署 | 项目部署（修复前） |
| --- | --- | --- |
| gstatic HTTP，每侧 12 次 | 延迟中位数 193.5 ms；176–680 ms | 延迟中位数 214.5 ms；177–332 ms |
| cp.cloudflare HTTP，每侧 8 次 | 中位数 192 ms；本地 204 | 中位数 1047.5 ms；另查响应确认为 400 |

在同一项目入口的临时测试节点中，显式指定同一区域 ProxyIP 的 80 端口，取得真实 Cloudflare 204，验证了端口修正方向。该实验不是 v1.0.6 的线上部署验收，也不是带宽测试；短时样本不能证明哪个版本长期更快。

## 固定订阅候选池

原版与项目默认都根据拉取订阅时的请求网络识别运营商，从 CIDR 池随机生成候选，并未逐个在用户线路测速。订阅请求经过境外代理时可能显示“CF 官方优选”；这与“CF 电信优选”的地址池不同。

v1.0.6 修复显式 `cnIspCode` 在订阅转换回源 URL 中被重新识别覆盖的问题。电信用户可在现有订阅 URL 后追加 `&cnIspCode=ct`；联通为 `cu`，移动为 `cmcc`，官方池为 `cf`。参数只固定候选池，不保证随机地址更快，也不改变隧道实际拨号的网络识别。已有自定义地址列表不受这一参数替代。

## 连接路径

| 模式 | v1.0.4 的白名单读取 | v1.0.5 的白名单读取 |
| --- | --- | --- |
| 无链式代理，直连 / ProxyIP 回退 | 每个隧道读取一次 KV | 0 次 |
| 全局 SOCKS5 / HTTP / HTTPS / TURN / SSTP | 每个隧道读取一次 KV | 0 次 |
| 按白名单选择的非全局链式代理 | 每个隧道读取一次 KV | 保留一次，以取得该请求的路由快照 |

判断依据是已解析的节点路径与查询参数，包含代理别名和编码链式路径。跳过读取不会改变出口选择。需要白名单时仍读取已保存的配置，没有额外引入长期应用缓存；已建立的连接保留自己的快照。

面板保存 ProxyIP、链式代理账号、全局模式或传输协议后，需要在 Clash Verge **更新订阅**。这些设置通过节点路径传递给隧道；白名单才是运行时读取 KV 的例外。Cloudflare KV 仍遵循自身的最终一致性与缓存规则。

## 请求隔离与内存工作

- 默认直连并发保留为 2，中国移动网络为 1；ProxyIP 候选并发保留为 1，DoH 预加载竞速默认关闭。
- 拨号参数现在是每个请求独立的不可变快照。移动网络请求不会再让后续其他运营商的默认并发一直停留在 1；后来的请求也不会改写已打开隧道的参数。
- `TCP_CONCURRENT_DIAL` / `PROXY_CONCURRENT_DIAL` 取正有限数并向下取整，限制为 1–6；无效值回退到该请求的默认值。Cloudflare 对同一调用的待建立出站连接设有 [6 个并发限制](https://developers.cloudflare.com/workers/platform/limits/#simultaneous-open-connections)，提高数值不等于提高带宽。
- 保留原版 1000 ms TCP 建连超时，成功、失败、超时后都清理对应定时器。
- gRPC 先完整验证 protobuf，只有一个数据字段时返回原缓冲视图，省去一次载荷分配与复制。MultiHunk 仍正确合并多个字段，非法尾部仍报错。

## 测速必须经过真实出口

原版及 v1.0.4 对 `speed.cloudflare.com`、`cp.cloudflare.com` 及其子域有特殊处理：无链式代理时在 Worker 本地返回 HTTP 204，不访问目标。这会让部分 HTTP 延迟结果只反映入口，且可能干扰访问这些域名的 TLS 数据或实际下载。

v1.0.5 删除这项特殊处理。VLESS / Trojan 的 WS、gRPC、XHTTP 以及 Shadowsocks 的 WS 都按普通目标转发，测速网站的 HTTP 请求与 TLS 数据也经过实际 socket / 回退出口。

升级后，这些地址的延迟数字可能上升，原先被短路的出口问题也可能表现为测试失败。v1.0.5 的 HTTP 80 回退错误已在 v1.0.6 修正；用户显式指定不支持 HTTP 的端口时，仍需使用适合目标协议的出口。应结合真实页面与下载判断，不能用旧版的本地响应和新版的完整链路耗时直接比较。

## 在 Clash Verge 验收

1. 用构建后的完整 `dist/_worker.js` 或 `dist/brclio-edge-pages.zip` 更新部署；不要只复制 `src/worker.js`。核对后台版本为 `1.0.7`，然后更新客户端订阅。
2. 对照原版 / 旧版时固定入口 IP、端口、协议、节点路径中的 ProxyIP 或链式出口；保持 Clash Verge 的测试 URL、统一延迟开关、DNS 和网络环境一致。
3. 选固定节点交替测几轮，分开记录首次和后续请求、失败次数、延迟中位数；避免同时测试大量节点把本地网络占满。
4. 另选固定目标文件，在同一出口下有限次下载，记录耗时和实际收到的字节。延迟的 ms 与吞吐量的 Mbps / MB/s 是不同指标。
5. 若仍使用随机生成的 16 个入口，先在自己的网络筛选后保存到地址列表，并关闭随机地址模式、更新订阅。默认的随机候选没有经过用户网络实测；切换入口与切换出口应分开验证。

本地回环测试用于确认真实转发、配置隔离、零 KV 读取与协议正确性，不能代表公网加速幅度。实际效果还取决于本地运营商、Cloudflare 入口、出口服务和目标站点。自动化验证记录见 [validation.md](validation.md)。
